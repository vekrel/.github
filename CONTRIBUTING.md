# Contributing

Vekrel is early. We are not actively seeking outside contributions yet and have limited review capacity. Opening a PR does not oblige us to review or merge it; we may close or defer it, ask for a smaller scope, or reimplement the idea later.

## Before you start

- Report bugs as issues in the repository they belong to, using the bug report form. Search first.
- Features and intentional behavior changes need a feature request issue with explicit maintainer approval of the direction and scope before you write code. Link that approval in your PR.
- A very small, focused fix for an obvious bug can go straight to a PR. Explain the defect and why the fix qualifies.

## Pull requests

- Solve one problem per PR. Split independent fixes.
- Describe what you verified and what you could not check. "Tests pass" alone is not enough. For UI changes, include before and after screenshots.
- Use a plain-language conventional commit title, such as `fix(web): new threads no longer spike CPU`.
- Each repository's README covers its setup and checks.
